# DESIGNSPEC.md — hakolect

## 0. 前提
- 仕様書 v3_2 を基準にする
- 画面・API・導線中の `/bookmarks` 表記は `/hakolect` に読み替える
- 仕様書 12章の確定事項は固定し、UI都合で変更しない
- 仕様外の判断は 1.3 の設計思想「とりあえず入れて、あとで整理」「ページに飛ぶことを最短にする」を優先する

## 1. デザインの意図
hakolect は「管理画面」ではなく「すぐ投げて、すぐ見つけて、あとで整える」ための個人用ストック画面です。
見た目の主役は装飾ではなく、
- URLへ飛ぶ主動作の明快さ
- 未整理→整理の流れの軽さ
- 連続編集時の視線移動の少なさ
です。

## 2. 全体レイアウト方針
### PC（1024px以上）
- 左固定サイドバー + 上部ヘッダー + メインカードグリッド + 右詳細パネル
- 詳細表示はモーダル化せず、必ず右スライドイン
- 詳細パネル表示中もカード一覧を見せ続ける
- メイン余白は広すぎないようにし、一覧密度を保つ

### タブレット（768〜1023px）
- 左サイドバー常時表示（幅はPCより狭くする）
- カードは2〜3列
- 詳細はオーバーレイへ切替

### スマホ（767px以下）
- サイドバーはドロワー
- カードは1列の横長
- 詳細は中央モーダル
- 主操作を片手で触りやすい位置に置く（メニュー・追加・検索）

## 3. 主要UI仕様
### 3.1 ヘッダー
- 左: ページタイトル
- 中央: 検索バー（十分な幅を優先）
- 右: `+ Add`
- `+ Add` は常に見える主要CTA
- Quick Add は URL入力のみに限定し、説明文で「Unsortedに保存、詳細は後編集」を明示

### 3.2 サイドバー
- 上から `All` / `Unsorted` / フォルダツリー / `+ New folder`
- `Unsorted` はフォルダ風の見た目だが特殊ビューとして扱う
- 階層はインデントで明快に見せる
- ドラッグホバー時は背景色 + 境界強調でドロップ先を明示

### 3.3 カード一覧
#### PC/タブレット
- Compact card を基本とする
- 幅は固定寄り、列数はグリッドの auto-fit で調整
- 情報優先順位:
  1. OGP画像
  2. タイトル
  3. ドメイン
  4. コメント2行
  5. タグ
- カード本体クリック = 新タブで遷移（最重要、他動作を混ぜない）
- `…` メニューは副操作。誤タップ防止のためクリック領域をカード本体と分離

#### スマホ
- 左60px前後のOGP画像 + 右情報列
- `…` は常時表示
- コメントは1行でもよいが、詰まりすぎるならタイトルとURLの視認性を優先

### 3.4 詳細表示
#### PC
- 幅 300〜350px の右スライドイン
- 選択カードにアクセントボーダーを付与
- 表示モードと編集モードの差が視覚的に分かるようにする
- 編集モード時は Save / Cancel を右上固定で明示

#### モバイル/タブレット
- オーバーレイモーダル
- 内容順はPCと同一
- 閉じる導線を複数用意（×、背景タップ）

## 4. 視覚ルール
### 4.1 トーン
- 軽量、静か、実務的
- 派手な演出より「素早く読める」「迷わない」を優先
- Ghostやブログ管理画面のような重さではなく、個人ツールらしい軽快さ

### 4.2 余白
- 余白は広げすぎず、一覧密度を優先
- ただしカード内テキストは行間を詰めすぎない
- パネルやポップオーバーはコンパクトにまとめる

### 4.3 角丸・境界
- カード、パネル、ポップオーバーは中程度の角丸
- 境界線は薄く、ホバー/選択時だけ強める
- 編集中・選択中・危険操作のみアクセントを強くする

### 4.4 色の使い分け
- 通常状態はニュートラル基調
- 主操作、選択、編集中はブルー系アクセント
- 削除は赤
- Unsorted は通常フォルダと区別できるが、警告色にはしない

## 5. 実装判断の優先順位
実装時に迷ったら以下の順で判断してください。
1. クリック/タップで目的URLへ最短到達できるか
2. 追加時の入力負荷が増えていないか
3. 未整理→整理の連続操作が止まらないか
4. 一覧の情報密度が落ちすぎていないか
5. 12章の確定事項を壊していないか

## 6. ユイ向けの実装メモ
- ルーティング・APIパス・表示文言の `/bookmarks` は `/hakolect` に統一
- PC詳細表示だけは必ずサイドパネルで実装し、モーダルに寄せない
- Card全体クリックと `…` ボタンのイベント競合を避ける
- Quick Add は項目追加をしない。URL単独入力を維持
- Empty state は重く作り込まず、1アイコン + 短文で十分
- レスポンシブ時の優先順位は「機能維持 > 装飾維持」

## 7. 今回ナナセの判断
今回のUIは「情報量を削る」のではなく、「主動作に関係ない迷いを削る」方向が適切です。
そのため、一覧はコンパクト、詳細は右で深く、追加は浅く、という3層構造で揃えるのが最も自然だと判断します。

## 8. 名称確定に伴うビジュアル方針
### 8.1 表記ルール
- 正式表記は常に `hakolect`（すべて小文字）を使う
- UIタイトル、ブラウザタイトル、OGP、README見出し、ロゴ検討時の本表記も `hakolect` に統一する
- 一時的な説明文で「bookmark manager」を併記してよいが、サービス名そのものを別表記へ揺らさない

### 8.2 ロゴ・タイポグラフィの方向
- 方向性は「個人の収集棚」よりも「軽快な収集動線」を感じるロゴが適切
- 字面は角を立てすぎないサンセリフ系が相性良い
- 装飾で“箱”を直訳しすぎず、整理・格納・再発見のテンポ感を優先する
- アイコン化する場合は、箱そのものより「スタック」「タブ」「収集済みの印」を抽象化した方がUIに馴染みやすい

### 8.3 OGP / ファーストビューの見せ方
- OGPや紹介画像では「大量管理」より「すぐ保存して、あとで整える」を短く伝える
- 画面キャプチャを使う場合は、カード一覧 + 右詳細パネルの2層構造が一目で分かる構図を優先する
- 配色は既存UIと同じくニュートラル基調 + ブルーアクセントを維持し、名称変更に引っ張られて別トーンへ飛ばない

## 9. 公開時に必要な見た目まわりの確認項目
### 9.1 最低限の公開チェック
- ブラウザタイトルは `hakolect` で統一し、旧 `bookmarks` 表記が残らないこと
- ヘッダー見出し、Empty state、ボタン文言、README見出しのサービス名がすべて `hakolect` で揃っていること
- favicon / OGP / 共有時タイトルのいずれかが未設定なら、素のVite初期値や汎用アイコンを公開状態のまま残さないこと
- `/hakolect/` 配下で開いたときに、余白崩れ・フォント欠落・配色崩れが初回表示で起きないこと

### 9.2 先回りで用意しておくと良い素材
- ロゴ未確定でも、文字ロゴとして使える `hakolect` のタイポ組みを1案持っておく
- OGP未制作でも、ニュートラル背景 + `hakolect` ロゴタイプ + 「save now, organize later」相当の短い補助コピーで暫定1枚を出せる状態にしておく
- 紹介画像が必要になった場合に備え、カード一覧 + 右詳細パネルが同時に見えるキャプチャ構図を基準カットとして決めておく

### 9.3 実装確認時の見る順番
1. PCで `/hakolect/` を開き、一覧密度・右詳細パネル・`+ Add` の主導線が意図どおり見えるか確認
2. スマホ幅で、カード1列表示と `…` メニューの押しやすさ、モーダルの収まりを確認
3. URL共有時のOGP、ブラウザタブ、README先頭の印象が同じトーンでつながっているか確認
4. 公開直前に、名称揺れ・初期画像・仮テキストの置き忘れがないかを全画面で見直す

### 9.4 判断基準
- 未完成でも「軽快に保存して、あとで整える」印象が伝わるなら公開可
- 逆に、初期テンプレ感や別プロダクト名の混入で信頼感を落とす要素がある場合は、機能完成より先にそこを潰す
- 装飾不足は許容してよいが、名称揺れと視覚ノイズの放置は避ける

## 11. 2026-05-11 再修正版 — 3点メニューは元UIのまま埋もれだけ解消する
### 11.1 今回の前提修正
- きよぴさんが求めているのは**別UI化**ではなく、**元の場所・元の押下位置・元の操作感を保ったまま、表示崩れだけを直すこと**
- したがって、bottom sheet や action sheet への切替は今回の要件に合わない
- 今回は「副操作の完遂性を上げるためにUI方式自体を変える」のではなく、**既存popoverの表示ロジックだけを補強する修正**として扱う

### 11.2 維持すべき体験
- `…` ボタンは今のカード右上・リスト右端のまま維持する
- タップ / クリックした直後に、その**ボタン近傍から小さなメニューが出る感覚**を変えない
- メニューの見た目（サイズ感・項目順・カードに紐づく印象）は極力そのままにする
- ユーザー視点で「別のメニューになった」と感じさせないことを合格条件に含める

### 11.3 何に埋もれているか
#### A. スマホ幅
- 主な問題は**ビューポート下端**へのはみ出し
- 画面下側のカードで `…` を押したとき、下方向表示のままだと全項目が収まりきらない

#### B. タブレット幅
- 主な問題は**ビューポート下端 / 右端** への衝突
- ただしここでも解決方法はUI切替ではなく、**popoverの反転・横ずらし**で吸収するのが今回の筋

#### C. PC + 右詳細パネル開放時
- 主な問題は**右詳細パネルとの視覚的・空間的干渉**
- 右列カードの `…` では、popover がパネル側へ寄りすぎると埋もれたように見えるか、押しづらく感じる
- ここも別UIへ逃がさず、**表示方向と座標調整**で解消する

### 11.4 採用する修正方針
- 3点メニューは**全画面幅でpopoverのまま維持**する
- 修正対象は「表示方式」ではなく、**popover の配置計算・安全マージン・積層順**に限定する
- 具体的には以下の3つで吸収する
  1. **上下反転**: 下に収まらないときは上に出す
  2. **左右クランプ**: 右端・左端を超えないように横位置を補正する
  3. **右詳細パネル回避**: 詳細パネル開放時は、その左端を実効右境界として使う

### 11.5 表示ルール
#### 基本位置
- 初期位置は従来どおり `…` ボタンの**右下寄り**から出す
- ボタンとの距離は 6〜8px 程度に留め、「押した場所のすぐ横に出る」感覚を残す
- **押下起点の rect が確定する前に `(0, 0)` や仮座標で描画しない**。座標未確定フレームでは非表示のまま待ち、アンカー座標取得後に初めて表示する
- したがって、左上飛び対策の最優先条件は「popover を描画する前に `anchorRect` と `menuSize` が取得できていること」とする

#### 位置計算の基準
- 位置計算の起点は常に `anchorRef.current.getBoundingClientRect()` とする
- `top` は `rect.bottom + offset` または `rect.top - menuHeight - offset` のどちらかから算出する
- `left` は `rect.right - menuWidth` を基準にし、ここから clamp する
- `top` / `left` のどちらかが `undefined` `NaN` 負の無限大になる場合は、その値で描画しない。**前回値を使い回すか、座標確定まで hidden のまま保持**する

#### 縦方向
- 下方向にメニュー全体が収まるなら、そのまま下に出す
- 収まらない場合のみ、同じアンカーに対して**上方向へ反転**する
- 上方向へ反転した場合でも、ボタンから極端に離さない
- 上下どちらにも完全には収まらない極端なケースでは、**見切れる側を作らず、より広い側へ寄せたうえで内部スクロール**を許容してよい
- ただしこの場合でも、起点は左上固定ではなく、あくまで押下ボタン近傍に留める

#### 横方向
- 基本はメニュー右端を `…` ボタン右端に合わせる
- 右端を超える場合は左へ寄せる
- 左端を超える場合は右へ戻す
- 横補正しても「別の場所に飛んだ」と感じない範囲に留める
- 横方向補正後も `left = VIEWPORT_MARGIN` に張り付いたままになるなら、それは衝突回避ではなく**起点計算失敗の疑い**として扱う

#### 右詳細パネル開放時
- 詳細パネルが開いているときは、**パネル左端 - 8〜12px** をpopover右端の限界とする
- 右列カードでは必要に応じて、ボタン基準のまま少し左へ逃がす
- それでも収まらない場合のみ上方向反転を優先し、パネルに重ねない
- 右詳細パネル開放時でも、メニューの見え始め位置は押下ボタン近傍から維持する

### 11.6 見た目と操作感の維持条件
- 項目順は `Detail / Edit / Move to... / Delete` のまま
- メニュー幅は現行相当（`w-44` 前後）を維持し、広げて別UIに見せない
- 角丸・影・区切り線・Delete の赤トーンも現行踏襲
- 開閉導線も現行踏襲（外側タップ、別要素クリック、Escape）
- body scroll lock のような「モーダル的な副作用」は入れない。あくまで小さなpopoverとして振る舞わせる

### 11.7 ユイ向けの実装条件
- `CardMenu` は全幅で `createPortal` + `fixed` のpopover表示を維持する
- `useActionSheet` のような別UI分岐は撤去し、**常にpopover**で完結させる
- 配置計算では `anchorRef.current.getBoundingClientRect()` を基準にする
- **初回描画時に `anchorRef.current` が未取得 / `menuHeight` 未確定なら、可視表示しない**。`visibility: hidden` などで1フレーム待ってから座標確定後に表示してよい
- `position` の初期値を `(0, 0)` 前提にしない。未確定状態は `null` などで持ち、左上表示のフォールバックを作らない
- 縦位置は `menuHeight` と `window.innerHeight` を見て、下方向優先・不足時のみ上反転にする
- 横位置は `window.innerWidth` と、詳細パネル開放時は `detailPanelRect.left` を使って clamp する
- `detailPanelRect` や `anchorRect` が取れない場合は、無理に補正計算を続けず、安全な通常popover位置にフォールバックする
- `anchorRect.width === 0 && anchorRect.height === 0` のような **無効rect** は有効座標として扱わない。DOM更新直後で rect が 0 のフレームは再計測を待ち、原点寄せ描画を作らない
- スクロール中やレイアウト切替直後にアンカーDOMが差し替わる場合は、**古いrectを保持したまま開き続けない**。再計測成功までは hidden に戻してよい
- z-index は右詳細パネルより上に置きつつ、視覚的にはあくまで小さな補助メニューに留める
- Grid と List で同じロジックを使い、押下位置だけが変わる状態にする
- メニューが高くなってもビューポート外へ欠けないことを優先し、必要なら `max-height` + `overflow-y-auto` を入れてよい
- 座標再計算は `open時` `resize時` `orientationchange時` `右詳細パネル開閉時` `scroll親移動時` に限定し、不要な再描画で座標が飛ばないようにする

### 11.8 本番前確認観点
#### 実機相当の幅
1. `390px 前後`（iPhone標準幅相当）
2. `768px〜820px 前後`（タブレット縦持ち相当）
3. `1280px 以上`（PC）

#### 押下位置
4. 一覧の**最下段カード右上**
5. 一覧の**右端列カード右上**
6. 一覧の**左端列カード右上**
7. List表示の**右端 `…` ボタン**

#### 右詳細パネル開閉
8. 右詳細パネル閉状態で自然位置に出る
9. 右詳細パネル開状態で、パネルに埋もれず押下位置近傍に出る
10. パネル開閉直後に `…` を押しても左上へ飛ばない
11. スクロール直後・レイアウト切替直後でも、`0x0 rect` や古いrect起点で別位置へ飛ばない

#### 合格条件
12. どのケースでも、popover の左上座標が `VIEWPORT_MARGIN, VIEWPORT_MARGIN` に張り付くような不自然な出方をしない
13. 押下した瞬間に左上へ一度見えてから移動する挙動を出さない
14. 修正後の見た目を初見で見たときに、「メニューの仕様が変わった」と感じない

### 11.9 今回のデザイン判断
- 今回は「改善」より「復元に近い修正」が正しい
- そのため、使い勝手を別UIで最適化するより、**元仕様を保ったまま崩れだけを潰す**方がきよぴさんの期待に一致する
- デザインとしては、目立つ変化を足さず、内部ロジックだけで破綻を消すのが最適解

## 12. 2026-05-12 追加整理 — 3点メニューの役割差分
### 12.1 今回の論点
- きよぴさん報告では `Detail / Edit / Move to...` が同じ挙動に見えており、**副操作の意味差がUI上で消えている**
- 現行実装上も、カード側の `onDetail` `onEdit` `onMove` がすべて `openDetail(bookmark.id)` に接続されているため、仕様差分が未反映の状態と整理できる
- この問題はラベル文言の違いではなく、**押下直後に入る状態・目的・次アクションが分かれていない**ことが本質

### 12.2 採用仕様（正本）
#### Detail
- 役割は **閲覧**
- 押下後は詳細パネル / オーバーレイを **表示モード** で開く
- 初期フォーカスは閲覧内容に置き、フォーム入力状態にはしない
- 右上には `Edit` 導線を見せてよいが、開いた瞬間から入力可能にはしない

#### Edit
- 役割は **即編集**
- 押下後は同じ詳細パネル / オーバーレイを **編集モード** で開く
- タイトル、コメント、フォルダ、タグが最初から編集可能状態になっていること
- ヘッダー文言・主要操作は閲覧時と切り替わり、`Save / Cancel` が即座に認識できること

#### Move to...
- 役割は **フォルダ移動を最短で完了すること**
- 押下後は「詳細を読む」より先に、**フォルダ選択UIへ直接入る** ことを優先する
- UIの実体は詳細パネル内編集モードを使ってよいが、その場合も開いた瞬間にフォルダ欄が主役として見え、移動操作へ直行できる必要がある
- 少なくとも `Move to...` 押下後に、通常の閲覧状態からさらに `Edit` を押さないと移動できない導線は不可

### 12.3 3導線の見え方ルール
- `Detail` と `Edit` は同じパネルを使ってよいが、**初期状態が視覚的に明確に違う**こと
- `Move to...` は `Edit` の下位互換ではなく、**フォルダ変更に目的を絞ったショートカット**として扱うこと
- したがって、3項目の差は以下で判別できる必要がある
  1. 開いた瞬間のヘッダー文言
  2. 入力欄が活性かどうか
  3. 主要CTA が `Edit` なのか `Save / Cancel` なのか
  4. 初回スクロールなしでフォルダ移動に着手できるか

### 12.4 推奨UI挙動
#### Detail の初期表示
- ヘッダーは `Item details`
- タイトル・コメント・フォルダ・タグは閲覧表現
- 右上に `Edit` アイコンを出す
- フォルダ名は静的表示でよい

#### Edit の初期表示
- ヘッダーは `Edit item`
- タイトル入力欄を活性化した状態で開く
- `Save / Cancel` を常時見せる
- 閲覧専用の説明文や装飾より、入力継続性を優先する

#### Move to... の初期表示
- ヘッダーは `Move item` または `Move to folder` など、目的が一目で分かる文言に切り替える
- 編集モードベースで開く場合も、初期視線はフォルダ選択UIへ集める
- フォルダ選択欄はファーストビュー内に置き、必要ならタイトル・コメントより上に一時的に再配置してよい
- 移動完了後はトースト等で完了を返し、一覧上の所属変更が認識できるようにする

### 12.5 ユイ向け実装メモ
- `openDetail(bookmark.id)` に加えて、**起動モード** を持てるようにする（例: `detail` / `edit` / `move`）
- カードメニューの `onDetail` `onEdit` `onMove` は、それぞれ別モードで同じ詳細UIを起動する
- 詳細パネル側では `initialMode` を受け、`editMode` の初期値とヘッダー文言を切り替える
- `move` モードでは `editMode=true` 相当で開きつつ、フォルダ欄へフォーカスまたは最上部表示させる
- smoke test には `Detail = 閲覧開始` `Edit = 編集開始` `Move to... = フォルダ移動開始` の3分岐確認を追加する

### 12.6 完了条件
- `Detail / Edit / Move to...` の3項目を同一人物が連続で試したとき、**それぞれ別の目的に入った**と迷わず認識できること
- `Move to...` が「詳細を開いただけ」に見えないこと
- ラベル差し替えだけでなく、**初期状態差分がDOMと視覚の両方で存在すること**

## 13. 2026-05-13 Phase 1-C UI差分整理
### 13.1 今回の対象と前提
- 対象は `Hakolect_Phase1開発計画.md` にある UI/UX差分のうち、以下の5点を先に固める
  1. フォルダ件数表示
  2. タグ候補サジェスト
  3. フルのフォルダパス表示
  4. スマホ1列カードレイアウト
  5. フォルダ移動導線
- ただし **フォルダ移動導線は Phase 1-B の move / reorder 実装にまたがる**ため、ここでは「UIの正本」を定義し、実装順は澪・ユイ側のPhase管理に合わせる
- 仕様判断は一貫して `save now, organize later` を最優先にする。保存直後に迷わせず、整理時に止めないことが合格条件

### 13.2 現状との差分整理
#### A. フォルダ件数表示
- 現状: `All hakolect` と `Unsorted` には件数が出るが、フォルダツリー各行には件数が出ていない
- 仕様: 各フォルダに `bookmark_count` バッジを出す
- 判断: 整理対象の濃淡を一目で読むために、件数は装飾ではなくナビゲーション情報として必要

#### B. タグ候補サジェスト
- 現状: 編集モードでは自由入力のみで、既存タグ候補が見えない
- 仕様: 前方一致サジェストを出し、Enter または候補クリックで確定
- 判断: 既存タグの再利用を促し、表記ゆれを増やさないため必須

#### C. フルのフォルダパス表示
- 現状: 詳細パネルでは末端フォルダ名のみ見えており、親階層が失われる
- 仕様: `Dev tools / Frontend` のようなフルパスを表示する
- 判断: 同名フォルダや深い階層での誤整理を防ぐため、末端名だけでは不足

#### D. スマホ1列カード
- 現状: 一覧グリッドは `grid-cols-2` 起点で、スマホ幅でも2列寄りに崩れやすい
- 仕様: 767px以下は常に1列の横長カード
- 判断: 片手操作でタイトル・ドメイン・`…` を確実に読めることを優先する

#### E. フォルダ移動導線
- 現状: ブックマーク移動はカードメニュー→`Move to...`→詳細パネル内で完了できるが、**フォルダ自体の Move to... が不足**している
- 仕様: フォルダコンテキストメニューから親フォルダ変更に入れる
- 判断: 「あとで整理」はブックマーク単体だけでなくフォルダ構造の調整まで含む。ここがないと整理導線が途中で切れる

### 13.3 採用仕様
#### 13.3.1 サイドバー件数表示
- フォルダ名の右端に、`All / Unsorted` と同じ密度感の件数バッジを表示する
- バッジは常時表示。hover時だけ出す仕様にはしない
- 数字は **直下件数** を基本とし、表示文言で集計方法を増やさない
- 0件フォルダも表示し続けるが、バッジは淡色にして「空」を読めるようにする
- 選択中フォルダでは、選択背景より一段濃い同系色バッジにして所属を見失わないようにする

#### 13.3.2 フルフォルダパス表示
- 表示箇所は最低2か所
  1. 一覧上部のパンくず
  2. 詳細パネル内のフォルダ表示
- 詳細パネル表示モードでは `Folder` ラベルの下に、`親 / 子 / 孫` を1行または2行までで表示する
- 末尾省略が必要な場合も **末端だけ残す省略** ではなく、先頭側を短縮して `/ Frontend / Docs` のように階層感を残す
- 編集モードのフォルダ選択では、`select` 内のインデント表示は維持してよいが、選択済み値の補助表示としてフルパスを近接表示してよい

#### 13.3.3 タグ候補サジェスト
- タグ入力欄は「自由入力欄 + 候補ドロップダウン」の組で扱う
- 入力が空でもフォーカス時に既存タグ上位を出してよいが、最低条件は **1文字以上入力で前方一致候補を出す** こと
- 候補は最大6件程度。長く出しすぎない
- すでに付与済みのタグは候補から除外する
- キーボード操作:
  - `↓ / ↑` で候補移動
  - `Enter` で選択中候補を確定
  - 候補なしで `Enter` の場合は新規タグとして確定
  - `Escape` で候補を閉じる
- 既存タグ再利用を主役にしつつ、新規タグ追加も邪魔しないこと

#### 13.3.4 スマホ1列カード
- 767px以下では **常に1列**。2列化しない
- レイアウトは仕様書どおりの横長カードに寄せる
  - 左: OGP 60px前後
  - 右上: タイトル + `…`
  - 右中: ドメイン
  - 右下: コメント1行 またはタグ1行
- スマホでは hover がないため、`…` ボタンは常時表示する
- タップ対象が近づきすぎないよう、カード本体と `…` の間に 8px 以上の安全域を持たせる
- 詳細パネルを開いて戻った後も、スクロール位置と1列表示を保つ

#### 13.3.5 フォルダ移動導線
- フォルダ行のコンテキストメニューに `Move to...` を追加する
- 起動後の第一目的は **親フォルダ変更**。rename と混ざらないUIにする
- UIは次のどちらでもよいが、優先は A とする
  - A. 小型ポップオーバー内で親フォルダ選択
  - B. 既存インライン編集位置を一時的に parent 選択モードへ切替
- 条件:
  - `Unsorted` は候補に含めない
  - 自分自身と自分の子孫フォルダは候補に含めない
  - 現在位置が分かる補助表示（Current: `Dev / Frontend`）を出す
  - 移動後はツリーの開閉状態を極力維持し、ユーザーを見失わせない
- この導線は Phase 1-B 側の reorder / tree 更新と接続されるため、UIだけ先に入る場合でも「ダミー導線」は作らない

### 13.4 画面別の見せ方
#### サイドバー
- `All hakolect` / `Unsorted` / 各フォルダの件数トーンを揃える
- 件数バッジは右端で縦位置を固定し、階層が深くなっても数字列が大きく揺れないようにする
- フォルダ行の `…` は hover 時だけでもよいが、スマホ/タブレットでは到達不能にならない表示条件にする

#### 一覧ヘッダー
- パンくず末尾の `N items` は維持しつつ、フォルダ選択時の階層を省略しすぎない
- 検索中にフォルダ文脈が消えるのは許容するが、検索解除で元の階層表示へ自然に戻ること

#### 詳細パネル
- 表示モード時のフォルダ情報は、単一ラベルではなく「所属の文脈」を見せる
- `Move to...` 起動時はフォルダ欄を最上段近くに置き、移動対象のタイトルは補助情報として短く添える
- タグ入力欄の候補は、パネル下部CTAと干渉しないよう上開きも許容する

### 13.5 ユイ向け実装メモ
- `GET /folders` の `bookmark_count` をそのまま使い、件数の別集計ロジックをフロントで増やさない
- フォルダパスは `folder_id` から毎回木をたどって生成してよいが、表示箇所が増えるなら共通ヘルパー化した方が安全
- タグ候補は `GET /tags` の結果を再利用し、まずはフロント内フィルタで十分
- スマホ1列カードは `grid-cols-1 sm:grid-cols-2 ...` のように **mobile first** で切り直す方が事故が少ない
- フォルダ移動導線は rename / delete と状態が競合しやすいので、同時に複数のインライン状態を持たない設計にする
- 詳細パネル内のフルパス表示は、APIが `folder_path` を返すようになっても UI上の見せ方責務は残るため、CSS上の省略ルールまで固定しておく
